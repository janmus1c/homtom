# Lessons learned (bring-up of homtom on the GO 630)

Append new entries as they happen. Format: symptom, cause, fix, how to recognise it again. Facts here were measured on the device unless marked *inference*.

## Workflow
- **Storage mode is the staging path.** Reboot with USB attached: the bootloader presents INTERNAL (moviNAND, FAT) and NO NAME (SD) to the Mac. Copy `ttsystem` to INTERNAL, then eject; the unit boots Linux. Ejecting INTERNAL alone was enough once (NO NAME refused to unmount but the boot proceeded). User-confirmed: a reboot lands in storage mode first.
- Always keep `ttsystem.lab2613` (stock-ish recovery) on INTERNAL; stage a candidate as `ttsystem` and keep a `ttsystem.ladder-<name>` copy under `artifacts/kernel-builds/homtom-6.1/`.
- Dev loop over the live link needs no storage mode: `tools/homtom-state|sh|put|wait`, `tools/devtools/devmem` (freestanding ARMv4T, built in Docker; upload with `homtom-put`).
- Build: `kernel/scripts/docker-build.sh` then `kernel/scripts/build-ttsystem-6.1.sh`; emulator check of init.sh: `kernel/scripts/test-initramfs.sh`.

## Toolchain / userland
- Debian's arm-linux-gnueabi glibc is **ARMv5TE**: static binaries built against it hit SIGILL (clz/blx) on the ARM920T. Use freestanding `-nostdlib -march=armv4t -marm` code with raw EABI syscalls, or the stock ARMv4T BusyBox (1.22.1, OABI, dynamic, glibc 2.3.2 libs; kernel has OABI_COMPAT).
- The stock BusyBox lacks `tail`, `nc`, `devmem`, `grep -E`, `uptime`; use `grep -e`, `sed`, `wc`.
- `telnetd` needs `/dev/pts` (`mount -t devpts devpts /dev/pts`) or it exits "can't find free pty".
- Raw shell: `tcpsvd 0.0.0.0 2323 /bin/sh`; the Mac side is `nc 192.168.1.10 2323`.

## Kernel
- User-mode hang: the early-boot colour macro after the MMU-enable `mcr` clobbered r0, which becomes `cr_alignment`; alignment_trap then rewrites CP15 c1 on every user exception and turns the MMU off. Never insert code between the `mcr` and `__mmap_switched` that touches r0/r1.
- The bootloader LCD framebuffer sits inside the decompressed kernel; relocate LCD DMA (we use phys 0x33F00000).
- Bootloader arms the watchdog: disable it in `map_io`. S3C2443 WDT needs WTCLRINT (+0x0C) acknowledged.
- `cachepolicy=writethrough` breaks early boot. `console=ttySAC0` stalls (no serial).
- Debug colour ladder is compiled out unless `HOMTOM_COLOR_LADDER` is defined; it was both flashy and slow (busy-wait pauses). Correction (2026-11-07): until then only the asm macros and board marks were gated; the 23 C-level TPAL marks that `apply-homtom.sh` inserts into start_kernel, setup_arch, setup_machine_tags and paging_init (`tpal_block`) were not, so every image up to ladder-inform still showed a white/magenta/green/.../gold colour sequence before the text console. They now sit inside `#ifdef HOMTOM_COLOR_LADDER` too.
- Text console (`homtom-fbtext.c`) is verbose by default; `homtom.quiet` or `/sys/kernel/homtom_splash` shows the brand splash.

## USB gadget (s3c-hsudc, g_ether ECM)
- macOS only brings the interface up after the device sends NETWORK_CONNECTION on the interrupt-IN endpoint; on first enumeration that notification is stuck (hsudc queues it waiting for TX_SUCCESS). A D+ pull-up drop/raise (`/sys/kernel/homtom_usb_pullup`, UCLKCON bit 31) behaves like a replug and fixes it.
- **Never use `soft_connect` disconnect/connect**: udc stop/start leaves USB dead until the device is rebooted.

## Reboot / power
- `reboot -f` currently powers the unit OFF (SWRST then WDT; WDT-only probably the same). Pinhole reset restarts normally. Open question; see `kernel/homtom/COLOR_LADDER.txt`. `/sys/kernel/homtom_reboot_mode` selects variants (0 SWRST+WDT, 1 WDT, 2 SWRST, 3 PWR_RST low + WDT).
- Power key: GPF0, active low (idle 1). PWR_RST GPJ10 high = power off.

## MMC (open)
- Stock 2.6.13 had /dev/mmcblk0 (SD) and /dev/mmcblk1 (INTERNAL). In 6.1 `mmc0` registers on s3c-sdhci.1 but no card shows; bootloader leaves GPE5-10 as outputs (GPECON 0x05155400); setting func 2 did not help; controller registers at 0x4a800000 read 0.

## Process
- Tool calls that wait on the device must be short (`timeout`); the user rejects long blocking probes.
- Self-referencing logs: the init loop echoes dmesg lines back into dmesg; grep patterns must not match your own `homtom-init:` lines or messages repeat forever on screen.

## RESOLVED: reboot (2026-11-06)
- Cause: TTBL reads INFORM0 (0x4C000070) after reset. 5 (watchdog) or 9 (software reset) prints "Reboot" and boots on; anything else (we left 1) is "Power down": it sleeps unless the power key is held. Found by disassembling the bootloader (0x30b03888, 0x30b0acf4); fix verified live: `devmem 0x4C000070 5; devmem 0x4C000044 0x533C2443`.
- Fix: `homtom_restart` writes INFORM0=5 then SWRST. A reboot with USB attached then lands in **storage mode** (INTERNAL/NO NAME on the Mac) by itself; eject INTERNAL to boot Linux. Never write INFORM0=3 (stage 1 may jump to INFORM1).
- `poweroff` currently also reboots (power_off falls through to restart); to be reworked.

## RESOLVED: MMC (2026-11-06)
- moviNAND is on **port L** (GPL0-7 DAT, GPL8 CMD, GPL9 CLK, function 2), controller HSMMC at 0x4A800000 (s3c-sdhci.1); GPE5-10 belong to the legacy SDI slot. Power GPJ14 low = on. Registers read 0 because runtime PM gated the clock when no card was found.
- Live proof: `devmem 0x560000F0 0x000A00AA 0x000F00FF`, then unbind/bind s3c-sdhci.1: /dev/mmcblk0 (2007040 KiB, no partition table, VFAT) mounts, read-write works. Board file now has `.cfg_gpio` for this.
- SD slot (NO NAME) is the legacy SDI controller (0x5A000000, `s3c2440-sdi`): CD GPF1 low, WP GPF7, power GPJ11 high, data GPE5-10. Not yet wired.
- With INTERNAL mounted from Linux, new `ttsystem` can be staged without storage mode (keep `ttsystem.lab2613` and `ttsystem.prev-*`).

## Autonomous cycle works (2026-11-06)
- The in-kernel `homtom_restart` (INFORM0=5 + SWRST) did NOT bring the unit back when reached via `reboot -f`, although the identical register sequence from userspace (`devmem`) worked twice. Cause not found (suspects: device_shutdown hooks or timing). Workaround: `/bin/reboot` (also poweroff/halt) in the initramfs is a script doing `sync; devmem 0x4C000070 5; devmem 0x4C000044 0x533C2443`. Use plain `reboot`, not `reboot -f`.
- /tmp is RAM: anything uploaded there (devmem) disappears on reboot; devmem is now baked into the initramfs (/bin/devmem).
- Tools: `tools/homtom-to-storage` (reboot, wait STORAGE), `tools/homtom-stage FILE` (copy to INTERNAL with ttsystem.prev backup), `tools/homtom-to-linux` (eject INTERNAL, force-unmount NO NAME, wait LINUX). Verified cycle LINUX -> STORAGE -> LINUX with no human action. The unit also mounts INTERNAL itself at boot as /mnt/internal (mmcblk0), so new images can be staged from Linux too.

## Safety net (2026-11-06)
- Watchdog reset works as recovery: with INFORM0=5 a stopped /dev/watchdog feeder resets the unit within ~15 s into storage mode (verified). init.sh sets INFORM0=5 (the bootloader resets it to 1 every boot) and runs a shell feeder. A kernel hang before userspace is NOT covered (the kernel leaves the WDT off).
- When the Mac's screen is locked, `diskutil eject` is dissented by loginwindow; use `diskutil unmountDisk force diskN` then eject (tools/homtom-to-linux does this).

## Storage mode needs an unlocked Mac (2026-11-06, unconfirmed but consistent)
- After the Mac screen locked (23:34:30) a reboot no longer produced storage mode: the Mac enumerates the bootloader (`GO 630`, 0x1390/0001) for ~2 s, then the bootloader boots Linux. TTBL enters storage mode only if the USB device controller sees a host bus reset/activity during its ~1000-tick window while ttsystem loads (bootloader static analysis, 0x30b14bf0 / 0x30b0b620). A locked Mac apparently does not configure the new mass-storage device in time. Not caused by INFORM, watchdog, SD module, or pull-up toggling (all tried).
- So: unattended nights have NO storage mode. Stage images from Linux instead (`cp` to /mnt/internal/ttsystem with ttsystem.prev), avoid kernel changes (a bad kernel strands the unit, nothing arms the WDT before userspace), and prefer reboot-free work (devmem, loadable modules via tools/homtom-put + insmod).

## Bluetooth chip alive (2026-11-07)
- CSR BC4 talks BCSP: with BT_MODE (GPB1) LOW, reset GPJ9 pulsed low/high, UART1 pins GPH2/3 (+10/11 for CTS/RTS) at function 2, the chip repeats a BCSP SYNC frame `c0 40 41 00 7e da dc ed ed a9 7a c0` (84 bytes in 2 s) at ~115200. With BT_MODE high the RX line stays low and nothing is sent. Next: hci_uart BCSP line discipline (needs `make modules`: bluetooth.ko, hci_uart.ko; artifacts/modules-6.1) and a BlueZ-less HCI client.
- BusyBox here lacks tr, dd, printf, cmp, md5sum, sleep with fractions. `echo -ne '\0NNN'` (octal with leading 0) sends raw bytes.
- First output of the raw shell on :2323 could be lost; tools/homtom-sh now sends a leading newline. stderr of the device shell is not returned: add 2>&1 in commands.
- /mnt/internal at boot may be the SD card; INTERNAL is the card with ttsystem.lab2613 (mmcblk0). tools/homtom-stage-live guards on that. Observed: the bootloader boots the ttsystem on INTERNAL (SD has none).

Load order on the device: ecc, ecdh_generic, libaes, serdev, bluetooth, hci_uart (+uinput). tools/devtools/hciattach (ioctl N_HCI + BCSP) creates hci0, tools/devtools/hcictl (up/cmd) is a raw HCI client. - RECOVERY TEST FINDING (2026-11-07 16:00): staged a deliberately hung image (init.sh = busy loop as its first line, ladder test-hung) to exercise tools/homtom-recover. The unit then needs the power key. So the recovery chain only worked for images that reach init (INFORM0 is written there) or reboot through our wrapper. Fix: the kernel board file now writes INFORM0=5 in homtom_map_io right after the system registers are mapped (commit "Kernel: set INFORM0=5 ..."), so any image whose kernel starts and later hangs resets into the Reboot path and its storage window. Images that never start a kernel (bad TTBL records) are still the bootloader's business. Also: never run a destructive failure test while the user is away unless the unit can come back without a physical key press.

- 2026-11-07 CORRECTION (storage-mode timing): the bootloader polls USB for about 1000 ticks right after USB init and takes the first host check BEFORE it reads ttsystem; with the Mac attached (or a Mac enumerating within that wait) storage mode starts first and draws from the NOR table; ttsystem is read only after the storage mode exits. So no ttsystem record can change storage-mode screens in the reboot-with-Mac flow (stage 1 on the unit confirmed: the changed id 263 never appeared; stage 0/1 images boot fine, so extra data records are accepted). Records can only affect screens drawn after the load (the FAT splash, or id 0 if the splash fails). Recovery for a bad graphics record is easy because storage mode precedes the load. See docs/STORAGE_GFX.md section 0.
